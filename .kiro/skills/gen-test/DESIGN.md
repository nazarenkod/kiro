# gen-test — механізм автоматичного створення UI-тестів через агенти

Дизайн-документ, версія 2. Описує мету, знайдений контекст проєкту, архітектуру
інструмента, повний пайплайн, метрики, структуру файлів та прийняті рішення.
Це креслення для реалізації скіла `.kiro/skills/gen-test/` і кастомних агентів
`.kiro/agents/`.

Статус: **approved design, у реалізації**. Усі відкриті рішення розділу 13
**закриті** 2026-07-25 — див. `DECISIONS.md` (рішення + наслідки) і оновлений
розділ 13. Лишається один блокуючий передпілотний чек (розділ 0).

> ⚠️ **Читати разом із `DECISIONS.md`.** Тіло документа (розділи 3–12) —
> первісне креслення. Рішення, що **змінюють** його і мають пріоритет:
> **13.3** (ревізія): live appium-mcp у дебазі не піднімається — три слої
> `static dump → reveal-скан → ескалація`; замість `DebugPause` будуємо
> хелпер `RevealScan` (скрол + дамп послідовності page source через штатну
> сесію тесту), парсинг — самописний (`mobile-locator-gen`); live appium — v2.
> **13.2** робить ТМ джерелом правди (регенерація при дрейфі). Додано
> **traceability-карту** (Q1) для верифікації відповідності ТМ. Де тіло
> згадує appium-attach/DebugPause — це знято/переформульовано; авторитетні —
> `SKILL.md`, агенти і `references/`.

Що змінилось відносно v1: платформа виконання (CLI замість IDE) і чек #6637;
скрол переведено з gap у штатну евристику кодогену; метрики розділено на
device/human/agent time; fetcher копіює тіла API дослівно; додано четвертого
агента `mr-composer`.

## 0. Передпілотний чек (блокуючий)

**Kiro issue #6637** (відкрито 23.03.2026): при програмному виклику кастомного
сабагента через `invokeSubAgent` у **IDE** поле `model` з frontmatter
ігнорується, виклик падає з «Invalid model. Please select a different model to
continue.» У **Kiro CLI** (`/agent swap`, делегування за `name`) модель
на агента працює штатно.

Наслідок: якщо пайплайн гоняти в IDE і баг живий, `tm-case-fetcher` і
`repo-scout` поїдуть на дефолтній моделі — і вся економія розділу 5
перетворюється на нуль при незмінній складності.

**Рішення: пайплайн виконується через Kiro CLI, не через IDE.** Там штатно
працює і модель-на-агента, і делегування за `name`, і паралель до 4 сабагентів;
заодно це шлях до батч-режиму (розділ 12).

Перед стартом реалізації перевірити на своїй версії:

1. Створити `.kiro/agents/probe.md` з `model: <дешева>`.
2. Делегувати йому тривіальну задачу з головного агента.
3. Переконатись, що виклик не падає і модель справді та, що в frontmatter.

Не працює і в CLI — тоді архітектура трьох агентів тримається лише на ізоляції
контексту, без економії на дешевих токенах; це вхід для рішення 13.8 (A/B
монолітом).

## 1. Мета

Перетворити перевірку критичного функціоналу з TestManager (ТМ) на робочий
Kotlin UI-тест у цьому репозиторії: компільований, зелений на Android, який
відповідає `conventions.md` і лежить у правильній теці `src/test/kotlin/tests/<feature>/`.

Ключові принципи:

1. Вхід — конкретний **блок** крит-функціоналу (`functionalId`) або **одна
   перевірка** (`checkId`).
2. Витяг опису блоку/перевірки — окремий кастомний агент на дешевшій моделі
   (ізоляція контексту + економія). Тіла API він **копіює дослівно**, не
   переписує.
3. Економія токенів — ієрархія дебагу: **дефолт — аналіз логу падіння**;
   live-інспекція через appium-mcp — лише gated-ескалація (attach до вже
   довезеної тестом сесії, точкові запити одного екрана, `NO_UI`, в
   ізольованому контексті debugger-а). **Вільне ходіння по екранах через
   MCP заборонене** — саме воно дороге.
4. **Зелений ≠ правильний.** Кожен згенерований тест проходить негативний
   контроль: доводимо, що він уміє падати (розділ 4, крок 7).
5. Прогалини даних (`gaps`) — не блокер і не привід вигадувати: їх закриває
   людина на чекпоінті плану.
6. Кожен прогін пайплайна лишає рядок метрик — автоматично, без ручного обліку
   (розділ 6). Час прогону розкладається на **device / human / agent**, інакше
   тезу про економію нема чим перевірити.
7. Навчання закриває наявний скіл `reflection` + журнал сесії — окремий
   механізм уроків не будуємо.

## 2. Знайдений контекст проєкту

### 2.1. Проєкт

- `ua.dig.autotests:privat24-ui-tests` — кросплатформні (iOS + Android) UI-автотести
  мобільного додатку Privat24. Проєкт **test-only**: увесь код у `src/test/kotlin`.
- Стек: Kotlin 2.1.10, JDK 21, Maven, TestNG 7.12, Selenide-Appium 7.16, WireMock 3.13,
  REST-Assured, Visual Regression Tracker, ReportPortal, TestManager-інтеграція.

### 2.2. Вхідний контракт (TestManager MCP)

Перевірено на App **2116** «Приват24 (new)» (team MT). Наразі там один
блок-шаблон «Сервіс» (`functionalId=16891`) з 16 перевірок.

`platformId`: `1`=Android, `2`=iOS, `3`=Cross-platform.

Структура однієї перевірки (`check`):

| Поле | Зміст |
|---|---|
| `checkId` | ID перевірки |
| `functionalId` | ID блоку, якому належить |
| `description` | Опис (HTML) |
| `request` / `response` | Очікуваний запит/відповідь API (JSON або XML) |
| `reproduceSteps` | `[{stepName, expectedResult}]` — кроки мануального сценарію (HTML) |
| `tagValidation` | `positive` / `negative` |
| `tags` | Пріоритет `P1` / `P2` / `P3` |
| `state` | `manual` / `manual_only` |
| `flagAutomation` | `Y` / `N` — чи автоматизована |
| `flagRelevance` | `Y` (неактуальна) / `N` (актуальна) |

**Один `check` = один тест-кейс.** `reproduceSteps` — покроковий сценарій, який
треба перекласти у DSL-тест. Весь текст у HTML — його треба чистити.

Читаючі тули ТМ MCP: `app_crit_fun_blocks_read` (блоки по appId),
`app_crit_fun_checks_read` (перевірки по blockId), `platforms_read`, `app_tags_read`,
`app_test_data_read`.

### 2.3. Цільовий вихід — анатомія тесту

Еталон: `tests/base/BaseTest.kt` (lifecycle, `TestDslProvider`) і приклади на кшталт
`tests/authorization/AuthTest.kt`. Обовʼязкові елементи (з `conventions.md`):

- Клас наслідує `BaseTest()`, має `@Feature("...")` на рівні класу.
- Метод: `@Test(description="укр")`, `@Owner("LDAP")`, `@TMId(id)`, назва `test_XX_<TMId>`.
- Взаємодія з UI — лише через дозволені DSL: `screen{}`, `navigate{}`, `auth{}`,
  `stubFor{}`, `confirmation{}`, `visualTrack{}`, `api{}`, `device{}`.
- Дані всередині методу; юзер заданий явно (`Users.TEST_APPLE`); картка — цілим
  обʼєктом через `findCard{}`; стаби — лише з `JsonFilePath`.
- UI-елементи — через `PbComponents` (кнопки, поля, списки, дати тощо), не базові локатори.
- Скрол до елемента — наявний `scroll to element` (розділ 4, крок 3).

Тести дзеркалять фічі: ~100 тек у `src/test/kotlin/tests/` (напр. `transferToCard`,
`cardRequisites`, `deposits`, `eSim`). Кожній фічі відповідає тека екранів у `screens/`.

### 2.4. Артефакти падіння (основа дешевого дебагу)

- `target/logs/automation.log` — logback, повний лог прогону.
- `target/surefire-reports/` — звіти TestNG.
- Selenide → `build/reports`, завантаження → `build/downloads`.
- `UIAssertionError` від `toSelenideUiAssertionError()` містить **локатор,
  скріншот і page source** у момент падіння — це і є дешевий сигнал для дебагу.

### 2.5. Команди

```bash
mvn -s settings.xml test-compile                    # лише компіляція, без девайса
mvn -s settings.xml test -Dtest=<Клас>#<метод>      # адресний прогін одного тесту
mvn ktlint:format                                   # автоформат
```

**Усі виклики mvn у пайплайні йдуть через обгортку `scripts/phase.sh`** (розділ
6.1) — інакше device-time не міряється. Голий `mvn` у shell-кроках скіла
заборонений; за потреби зафіксувати правило хуком на перехоплення виклику тула.

`-Dtm.ids` для адресного прогону не годиться: пайплайн запускає конкретний тест
так, як TestNG на методі, через surefire — напр.
`-Dtest=AuthTest#test_01_12345`.

Платформа/режим — через `.env` (`PLATFORM=ios|aos`, `RUN_MODE`, `ENABLE_HUB`).

## 3. Архітектура

Скіл-оркестратор `gen-test` + чотири **кастомні агенти** в `.kiro/agents/`.
Навчання делеговане `reflection`.

```
              /gen-test <functionalId | check:checkId>        /gen-test mr
                                   │                               │
                     ┌─────────────▼─────────────┐                 │
                     │   Головний агент (skill)   │                 │
                     │  план · кодоген · оркестр  │                 │
                     │  негативний контроль ·     │                 │
                     │  метрики                   │                 │
                     └──┬────────┬───────────┬────┘                 │
            fetch (∥)   │        │ scout (∥) │  debug               │ mr
                        ▼        ▼           ▼                      ▼
        ┌────────────────┐ ┌──────────────────┐ ┌──────────────┐ ┌──────────────┐
        │ tm-case-fetcher│ │ repo-scout        │ │ui-test-      │ │ mr-composer  │
        │ model: дешева  │ │ model: дешева     │ │debugger      │ │ model: дешева│
        │ TM MCP + read  │ │ read/grep, БЕЗ    │ │model: дефолт │ │ read + shell │
        │ TM → строгий   │ │ write             │ │read+shell+   │ │ (git) +      │
        │ спек, тіла API │ │ репо → мапа       │ │appium(read)  │ │ gitlab MCP   │
        │ дослівно       │ │ + скрол-факти     │ │БЕЗ write     │ │ шаблон+цифри │
        └────────────────┘ └──────────────────┘ └──────────────┘ └──────────────┘
```

Чому саме так:

- **`tm-case-fetcher`** — механічна робота (тягнути, зрізати HTML, скласти спек
  за схемою). Дешева модель класу Haiku, тули обмежені читаючими тулами ТМ MCP.
  Важкий HTML лишається в його контексті. **Тіла `request`/`response` він
  копіює дослівно** і лише валідує на parseable — переписування JSON/XML
  моделлю є джерелом тихих семантичних помилок (розділ 4, крок 1а).
- **`repo-scout`** — розвідка репозиторію: чи є вже тести цього блоку і як
  вони влаштовані, яка фіча-тека, які екрани/компоненти/стаби існують, **де в
  наявному коді вже застосовано скрол**. Обхід десятків файлів лишається в
  контексті скаута; головний агент отримує компактну мапу. Тули: лише
  read/grep, без write. Запускається **паралельно** з fetcher — обидва входи
  для PLAN готуються за один такт.
- **`ui-test-debugger`** — аналіз стектрейсів і page source вимагає міркування,
  модель дефолтна. Тули: read + shell (перезапуск на вимогу) + **read-тули
  appium-mcp** (attach/detach, get_page_source, generate_locators,
  find_element, gesture-scroll, screenshot) — live-інспекція виконується
  **в його контексті**. **Без write** — агент фізично не може «полагодити»
  тест переписуванням, лише повертає діагноз і точковий фікс. Застосовує фікс
  головний агент — це і safety-guard, і гарантія, що фінальний код проходить
  через один контекст, який знає `conventions.md`.
- **`mr-composer`** — складання MR за людським шаблоном + блок доказів.
  Робота шаблонна, модель дешева. **Цифри рахує скрипт**, не модель
  (розділ 4, крок 10).
- Оркестрація, план, кодоген, негативний контроль і запис метрик — у головного
  агента: це кроки, де потрібен повний контекст рішень.

## 4. Пайплайн

```
1. FETCH ∥ SCOUT  паралельно: tm-case-fetcher (TM → строгий спек + gaps[])
                  і repo-scout (репо → мапа: наявні тести блоку, еталон,
                  екрани, скрол-факти, стаби, gaps репозиторію)
2. PLAN           головний агент: джойн спека і мапи → user, card, deeplink,
                  stubs, feature-тека. Обʼєднані gaps → питання людині.
                  → ЧЕКПОІНТ (risk-based: авто лише якщо gaps порожній
                    і всі ресурси зарезолвлені)
3. CODEGEN        тест за conventions.md, еталон — template від скаута;
                  скрол — за евристикою позиції; брак екрана/компонента =
                  ФЛАГ, не вигадка
4. COMPILE        phase.sh compile → mvn test-compile → фікс inline (без девайса)
5. RUN AOS        phase.sh run_aos → mvn test -Dtest=<Клас>#<метод>
6. DEBUG          ui-test-debugger: класифікація падіння → точковий фікс →
                  повтор (bounded: 3 змістовні ітерації; flaky — поза лімітом;
                  unknown → live-інспекція або ескалація)
7. NEG-CONTROL    зламати цільовий ассерт/стаб → прогін МУСИТЬ впасти → git revert
8. VERIFY iOS     обовʼязково після зеленого AOS (для cross-platform перевірок)
9. REPORT         підсумок + шлях + TMId + рядок метрик у runs.jsonl;
                  запис у журнал → reflection
─────────────────────────────────────────────────────────────────────────────
10. MR            окремою командою, не автоматично: mr-composer збирає MR
                  за шаблоном з .gitlab/ + блок доказів + цифри від mr_stats.py
```

### Крок 1а. FETCH (агент `tm-case-fetcher`)

Вхід: `functionalId` або `checkId`. Дії: тягне дані через ТМ MCP
(`app_crit_fun_checks_read` / `app_crit_fun_blocks_read`), зрізає HTML і повертає
спек **строго за схемою**. Спек без обовʼязкових полів головний агент відхиляє
і перезапитує — сміття на вході каскадує в усі наступні кроки.

**Правила щодо тіл API (критично).** `request`/`response` — це контракт, на
який зав'яжуться стаби. Модель, яка «чистить і переформатовує» JSON/XML,
рано чи пізно мовчки перейменує поле або зʼїсть вкладеність, і тест
перевірятиме не той контракт, лишаючись зеленим. Тому:

- тіла копіюються **дослівно**, як прийшли з ТМ, без переформатування,
  перекладу ключів чи «виправлення» синтаксису;
- єдина дозволена дія — валідація: parseable / not parseable. Not parseable
  → це `gaps[]`, не привід чинити;
- HTML-стрип описових полів (`description`, `reproduceSteps`) робить
  **детермінований скрипт**, не модель.

Через це роль моделі у fetcher-і зводиться до розкладання кроків по схемі;
якщо після пілоту виявиться, що і це стабільно робиться скриптом — агент
можна замінити скриптом цілком (кандидат у розділ 12).

```yaml
check_id: <int>            # обовʼязково
title: <str>               # обовʼязково
priority: P1|P2|P3         # обовʼязково
platform: aos|ios|cross    # обовʼязково
validation: positive|negative
preconditions: [<str>]
steps:                     # обовʼязково, ≥1
  - action: <str>
    expected: <str>
api:
  request:  <дослівно з ТМ | null>
  response: <дослівно з ТМ | null>
  parse_ok: true|false     # результат валідації, не виправлення
gaps:                      # обовʼязково (може бути порожнім списком)
  - <що не вдалося витягти: плейсхолдер у кроці, порожній expected,
     невалідний JSON у response, суперечність кроків тощо>
notes: <str|null>
```

`gaps[]` — перше поле, на яке дивиться головний агент. Плейсхолдери й
недописані перевірки в ТМ — норма; fetcher їх **фіксує, а не інтерпретує**.

### Крок 1б. SCOUT (агент `repo-scout`, паралельно з FETCH)

Вхід: `functionalId`/`checkId` + назва блоку. Скаут може стартувати **без**
спека від fetcher: тести маркуються `@TMId`, тож пошук наявних тестів цього
блоку/сусідніх перевірок — це grep за ID, відомими вже з аргументів виклику.

Дії:

1. **Наявні тести блоку**: grep `@TMId` по `tests/` за checkId-сусідами
   `functionalId`. Знайшлись — розібрати, як влаштовані (навігація, user,
   стаби, ассерти), і призначити найближчий за флоу **template-тестом**.
   Переюз існуючого патерну майже завжди кращий за генерацію з нуля.
2. **Мапа релевантної частини проєкту**: фіча-тека в `tests/`, відповідні
   екрани в `screens/` та їхні ключові `PbComponents`, наявність діплінка,
   існуючі стаби. Не «вся ієрархія проєкту» — лише зріз під цей блок.
3. **Скрол-факти**: до яких елементів цих екранів у наявному коді вже
   застосовується `scroll to element`. Це головне джерело знання про позицію
   елемента у вьюпорті — з `reproduceSteps` вона не виводиться (крок 3).

Вихід — строгий контракт (аналогічно fetcher):

```yaml
feature_dir: tests/<...> | null
block_tests:                # вже існуючі тести цього блоку
  - {path, tm_id, flow: <1 рядок>}
template_test: <path|null>  # еталон для кодогену
screens:                    # екран → ключові компоненти
  - class: <Screen>
    components: [...]
    scrolled_elements: [...]   # до чого в наявному коді вже застосовано скрол
deeplink: <клас|null>
stubs_existing: [<JsonFilePath>]
gaps:                       # чого в репо немає: екран, компонент, стаб
  - <...>
```

Кеш: для батчу перевірок одного блоку мапа переюзається (скаут запускається
раз на блок, результат — у `target/gen-test/scout-<functionalId>.yaml`).

### Крок 2. PLAN (головний агент, risk-based чекпоінт)

Вхід — два артефакти: спек від fetcher і мапа від scout. Головний агент **не
обходить репозиторій сам** — він джойнить і вирішує:

- **feature-тека / екрани / template**: з мапи скаута.
- **user**: підбір з `Users.*` за передумовами спека (роль, тип рахунку).
- **card**: критерій для `findCard{}` (тип, валюта).
- **навігація**: діплінк (з мапи) чи через home screen.
- **стаби**: які `JsonFilePath` потрібні під `request/response` спека; що з
  цього вже існує (з мапи).
- **прогалини**: обʼєднання `gaps` спека (дані ТМ) і `gaps` мапи (репозиторій).

**Робота з gaps.** Кожен елемент обʼєднаного `gaps[]` перетворюється на
конкретне питання людині на чекпоінті («у кроці 3 плейсхолдер `{сума}` — яку
суму використати?», «екрана X немає — створюємо чи міняємо флоу?»). Відповіді
вливаються в план. Агент **не заповнює прогалини здогадками**.

**Правило чекпоінта (risk-based):**

- Авто-прохід: `gaps` порожній **і** всі ресурси зарезолвлені
  (feature-тека знайдена, user/card підібрані, всі стаби існують, екрани є).
- В усіх інших випадках — пауза на людину: план + список питань.

План пишеться у файл (`target/gen-test/plan-<checkId>.md`), а не лише в чат —
переживає сесію, можна дивитись diff. Момент паузи і момент відповіді
маркуються в метриках (`human_seconds`, розділ 6.1).

### Крок 3. CODEGEN (головний агент)

Генерація тест-класу строго за `conventions.md`. Правила:

- Переюз наявних екранів; якщо екрана/компонента немає — **не галюцинувати**,
  а позначити прогалину і зупинитись/запитати.
- Стаби лише з `JsonFilePath`; юзер і стаби узгоджені.
- **Колізія стабів**: якщо файл маппінгу з такою назвою вже існує — не
  перезаписувати і не перейменовувати самовільно. Ескалація людині:
  «переюзати наявний / створити під новою назвою (запропонувати)». Рішення
  фіксується в плані.
- **Еталон — `template_test` від скаута**: генерація «за зразком найближчого
  існуючого тесту», а не з нуля. Немає template — генерація з `conventions.md`
  + приклади з мапи, з підвищеною увагою на чекпоінті.
- API бібліотек **не** уточнюємо зовнішніми джерелами (context7 тут зайвий):
  усе потрібне вже є в репозиторії — мапа скаута і template це покривають.
- Після кодогену зафіксувати hash згенерованого файлу (для метрики
  `code_edited_by_human`, розділ 6).

#### Скрол — штатна евристика, не gap

У проєкті **є** `scroll to element`. Правило:

- елемент у **верхній** частині екрана → взаємодія без скролу;
- елемент **ближче до низу** → скрол додається **одразу в метод взаємодії**
  з елементом, а не окремим кроком сценарію.

Задача агента — визначити позицію. Джерела за спаданням дешевизни:

1. **Скаут** (`scrolled_elements`): якщо до цього елемента/аналогічного в
   наявному коді вже застосовується скрол — застосовуємо. Основне джерело,
   безкоштовне.
2. **Template-тест**: як влаштована взаємодія з тим самим екраном у
   найближчому тесті.
3. **Невідомо** → діє дефолт, зафіксований у `references/codegen.md`
   (див. відкрите рішення 13.6: дефолт залежить від того, чи є
   `scroll to element` no-op на вже видимому елементі).
4. **Live-інспекція** (лише у дебазі, не превентивно): `appium_gesture
   action=scroll_to_element` з `maxScrollAttempts` і детекцією стабілізації
   page source дає факт «елемент досяжний за N скролів, локатор такий-то».

Наслідок для дебагу: підклас `locator` «елемент поза вьюпортом» стає
авто-фіксом першої ітерації («обгорнути скролом»), без live-інспекції.

**Метрика `scroll_fix`** — скільки разів рішення по скролу довелось правити
(додати відсутній / зняти зайвий) у дебазі або людиною. Частка > 30% означає,
що евристика неправильна, і це видно після пілоту, а не через півроку.

### Крок 6. DEBUG (агент `ui-test-debugger`)

На падінні агент читає **лише артефакти** (`target/logs/automation.log`,
`target/surefire-reports`, стектрейс `UIAssertionError` з локатором + page source).

**Спершу класифікація, потім фікс.** Кожне падіння відноситься до одного з класів:

| Клас | Ознаки | Стратегія |
|---|---|---|
| `locator` | елемент не знайдено; локатор не бʼється з page source | виправити селектор/компонент |
| `scroll` | елемент є в page source/дереві, але поза вьюпортом | обгорнути взаємодію скролом (авто-фікс, крок 3) |
| `stub` | у лозі запит без відповідного маппінгу / mismatch тіла | виправити стаб або `stubFor{}` |
| `data` | user/card не відповідає передумовам, помилки авторизації | змінити тест-дату у плані |
| `flow` | впав не той крок, екран інший за очікуваний | переглянути навігацію/послідовність |
| `env` | таймаути девайса/хаба, з'єднання, «мигання» без змін коду | ретрай без змін |
| `unknown` | впевнено не підпадає під жоден клас | не вгадувати: live-інспекція або ескалація |

Правила петлі:

- Ліміт: **3 змістовні ітерації** (фікс → перезапуск).
- Підозра на `env`/flaky → **один ретрай без жодних змін**, і він **не
  витрачає** ітерацію з трьох. Впав знову тим самим чином — це вже не flaky,
  класифікувати заново.
- Агент повертає: клас падіння + діагноз + конкретний фікс (diff-подібно).
  Застосовує головний агент.
- Вичерпано ліміт → ескалація людині зі зведенням усіх діагнозів.
- Кожен перезапуск — через `phase.sh` (фаза `retry`).

**Live-інспекція через attach (appium-mcp).** Для `unknown` лог не дає
відповіді — треба живий екран у стані падіння. Наш MCP — офіційний
`appium/appium-mcp`; `appium_session_management action=attach` підключається
до **вже відкритої сесії на remote Appium-сервері за sessionId, без
перехоплення ownership**: друга сесія не створюється (конфлікту uiautomator2
немає), а при disconnect MCP видаляє лише owned-сесії — attached лишається
живою.

Розподіл ролей: **оркестратор** робить усе, що потребує write (вставка/зняття
паузи, запуск прогону); **attach та інспекцію виконує `ui-test-debugger`** у
своєму контексті — важка XML-ієрархія і JSON локаторів не потрапляють у
головне вікно. Механіка:

1. **Пауза.** Утиліта `DebugPause.here()` у тест-інфрі (одноразова людська
   задача, ~20 рядків): активна лише при `-Dgen.test.pause=true`; пише в лог
   `GEN-TEST PAUSED` і чекає файл `target/gen-test/.resume`. Оркестратор
   тимчасово вставляє виклик перед кроком падіння, запускає тест у фоні —
   тест сам довозить апку до цільового екрана і тримає сесію відкритою.
2. **Attach.** sessionId ловить наявний хук `capture-session-id` (запасний
   варіант — парсинг automation.log); URL сервера — з `.env`. Виклик:
   `appium_session_management {action: attach, remoteServerUrl, sessionId}`.
3. **Інспекція** тією самою сесією: `appium_get_page_source`,
   `generate_locators`, `appium_gesture action=scroll_to_element`,
   `appium_find_element` (пріоритет: accessibility id > id > платформні
   стратегії > xpath як крайній), `appium_screenshot` за потреби.
4. **Завершення.** `action=detach`; фоновий прогін **убити, а не resume**:
   скрол-жести змінили стан екрана. Тимчасову паузу прибрати
   (`git checkout`). Діагноз — у debugger, фікс — штатною петлею.

Конфіг appium-mcp: `NO_UI=true` (відповіді без HTML-обгорток, економія
60–90% токенів). Опційно `APPIUM_MCP_EVIDENCE=true` — структурний запис
дій у відповідях `find_element`/`gesture`, зручно для розбору.

Live-інспекція вмикається лише після безрезультатної лог-ітерації; факт
використання — у метрики (`appium_fallback_used`). Див. відкрите рішення 13.3:
на пілоті цю підсистему можна не будувати взагалі.

### Крок 7. NEG-CONTROL — негативний контроль (обовʼязковий)

Зелений тест ще не означає правильний: слабкі ассерти або перестаблений флоу
проходять, нічого не перевіряючи. Тому після першого зеленого прогону:

1. Головний агент вносить **одну мутацію** — **саме в той ассерт, який мапиться
   на `expected` цільового кроку перевірки** (або в поле стаба, від якого цей
   ассерт залежить). Мутація випадкового поля доводить менше: вона показує, що
   тест взагалі вміє падати, але не що він перевіряє потрібне.
2. Прогін (`phase.sh neg_control`). Тест **мусить впасти**.
3. `git checkout` мутованих файлів — повернення до зеленого стану без
   повторного прогону.

Впав → контроль пройдено, у метрики `negative_control: pass`. Не впав →
`fail`, тест **не вважається готовим**: розбір ассертів з людиною обовʼязковий.

Межі методу (щоб не переоцінювати): одна мутація — це перевірка живості
цільового ассерта, не мутаційне покриття. Вона **не ловить** випадок, коли
контракт стаба спочатку неправильний (тому крок 1а вимагає дослівного
копіювання тіл API).

Ціна — один додатковий прогін на тест; на пілоті обовʼязково для 100% кейсів,
далі можна перейти на вибірковий режим за результатами.

### Крок 8. VERIFY iOS (обовʼязково для cross-platform)

Після зеленого AOS і пройденого neg-control — обовʼязковий прогін
`PLATFORM=ios` того самого тесту (`phase.sh run_ios`). Падіння на iOS іде в ту
саму debug-петлю (окремий бюджет: 3 ітерації; типові класи — `locator`,
`scroll` і платформна специфіка). Для перевірок `platform: aos` крок
пропускається. Тест вважається готовим, лише коли зелені **всі** платформи
його перевірки.

Після пілоту — кандидат на вибірковість (відкрите рішення 13.4): iOS-прогін
найдорожчий у пайплайні за device-time.

### Крок 9. REPORT + метрики + навчання

- Короткий підсумок: шлях до тесту, TMId, статус AOS/iOS, negative control,
  знайдені прогалини і як закриті.
- Дописати рядок у `metrics/runs.jsonl` (розділ 6) через `scripts/log_run.py`
  (він же дочитує `phases-<checkId>.jsonl`).
- Уроки — у журнал сесії; наприкінці — `reflection`.
- Позначення перевірки як автоматизованої в ТМ — **ручне**. Автофліп
  `flagAutomation` небезпечний саме через ризик «зелений ≠ правильний».

### Крок 10. MR (агент `mr-composer`, окрема команда)

Не частина автоматичного пайплайна: запускається окремо (`/gen-test mr`), коли
людина вирішила, що набір тестів готовий до рев'ю.

**Шаблон.** Джерело правди — `.gitlab/merge_request_templates/*.md`, людський
файл у репо. Агент його **читає і заповнює**, не переписує; зміни шаблону
підхоплюються без правок скіла.

Важливо: GitLab підставляє шаблон автоматично лише в UI. При створенні MR
через API/MCP описання передається цілим у поле `description` — тобто агент
**зобовʼязаний сам** прочитати потрібний `.md`, заповнити і віддати готовий
текст. Перевірити одним тестовим MR на своїй версії GitLab.

Правила заповнення:

- **Ім'я шаблону зафіксоване** в `mr-composer.md` або передається параметром
  команди — «агент обере відповідний» це недетермінізм на рівному місці
  (див. відкрите рішення 13.5: переюз наявного шаблону vs окремий `gen-test.md`).
- Заповнюються лише секції, під які є дані; секції **не видаляються і не
  переставляються**.
- Чек-листи рев'ювера агент **не відмічає** — це відповідальність людини.
- Мова описання — як у шаблоні.
- Блок доказів обгортається маркерами:
  `<!-- gen-test:evidence -->` … `<!-- /gen-test:evidence -->`. При оновленні MR
  регенерується **лише** цей блок, правки людини поза маркерами не затираються.

**Цифри рахує скрипт, не модель.** `scripts/mr_stats.py` парсить
`git diff --name-status origin/<base>...HEAD -- src/test/kotlin/tests/**` і
повертає JSON:

```json
{
  "added_tests":   {"count": 4, "tm_ids": [12345, 12346, 12350, 12351]},
  "changed_tests": {"count": 1, "tm_ids": [12001]},
  "files_added": 3, "files_changed": 2,
  "stubs_added": ["...json"]
}
```

Агент лише розкладає готовий JSON по шаблону — інакше цифри попливуть від
сесії до сесії, як і схема метрик.

**Блок доказів** (те, заради чого це варто робити): для кожного TMId —
платформи, `negative_control`, `debug_iterations`, `scroll_fix`, посилання на
прогін. Рев'ювер бачить, **що саме перевірено**, а не лише діф. Це прямий
важіль на час рев'ю — головну незміряну величину проєкту.

**Гейт:** MR не створюється, якщо для якогось TMId у діфі немає рядка в
`runs.jsonl` з `outcome=green` і `negative_control=pass`. Дешево, і переносить
принцип «зелений ≠ правильний» на межу з рев'ю.

**Гранулярність:** на пілоті — MR на чек (чистіша метрика рев'ю); у потоці —
на блок.

## 5. Економія токенів

| Важіль | Ефект |
|---|---|
| `tm-case-fetcher` на дешевій моделі, HTML в ізоляції | шумний HTML не в головному контексті + дешевші токени |
| `repo-scout` на дешевій моделі, обхід репо в ізоляції, кеш на блок | десятки файлів не осідають у головному контексті; template замість генерації з нуля скорочує debug-петлю |
| `ui-test-debugger` читає лог; live-інспекція — gated і в його ізольованому контексті | немає вільного ходіння по екранах |
| `mr-composer` на дешевій моделі; цифри — скриптом | шаблонна робота не займає дефолтну модель |
| `conventions.md` як always-джерело знань | кодоген не переводить щоразу API компонентів |
| debug-петля bounded (3 + flaky поза лімітом) | немає нескінченного циклу фіксів |
| Скрол як евристика кодогену, а не gap | менше ескалацій і менше ітерацій дебагу на списках |
| Android-first, iOS on-demand | менше повільних iOS-прогонів |
| Строга схема спека | немає повторних уточнень «а що малося на увазі» |

**Застереження.** Уся таблиця тримається на тому, що `model` у frontmatter
справді застосовується (розділ 0). І перевіряється вона не сумарною
тривалістю прогону — та на 80–90% складається з device-time, — а корзиною
`agent_seconds` (розділ 6.1).

## 6. Метрики

Мета: після пілоту відповісти цифрами, а не «вроді працює». Все збирається
автоматично оркестратором, без ручного обліку.

### 6.1. Збір

**Фази і device-time.** Кожен зовнішній прогін іде через обгортку:

```bash
scripts/phase.sh <check_id> <phase> -- <cmd>
```

Обгортка аппендить рядок у `target/gen-test/phases-<checkId>.jsonl`:

```json
{"check_id":12345,"phase":"run_aos","attempt":2,
 "ts_start":"...","ts_end":"...","duration_s":214,"exit_code":1}
```

Фази: `compile`, `run_aos`, `neg_control`, `run_ios`, `retry`. Ненульові
exit-коди і вбиті фонові прогони пишуться так само — саме вони найдорожчі.
Правило «mvn лише через `phase.sh`» фіксується в `references/run-and-debug.md`;
за потреби — хуком на перехоплення виклику тула.

**Три корзини часу.** Одна цифра тривалості нічого не пояснює:

- `device_seconds` — сума фаз із phases-файлу;
- `human_seconds` — сума інтервалів «питання на чекпоінті → відповідь»
  (оркестратор ставить маркер у момент паузи і в момент відповіді);
- `agent_seconds` = загальна тривалість − device − human.

Без вирахування `human_seconds` третя корзина — сміття, а саме вона потрібна
для порівняння «моноліт vs три агенти» (13.8) і для перевірки розділу 5.

**Рядок прогону.** Один прогін пайплайна = один рядок JSONL у
`.kiro/skills/gen-test/metrics/runs.jsonl`. Запис — через `scripts/log_run.py`
(валідує схему, дочитує phases-файл, ставить таймстемпи, аппендить).

```json
{
  "ts_start": "2026-07-23T10:00:00Z",
  "ts_end":   "2026-07-23T10:41:00Z",
  "check_id": 12345,
  "functional_id": 16891,
  "gaps_from_fetcher": 2,
  "checkpoint": "human",
  "plan_edited_by_user": true,
  "compile_fix_iterations": 1,
  "debug_iterations": 2,
  "flaky_retries": 1,
  "failure_classes": ["locator", "stub"],
  "scroll_fix": 0,
  "appium_fallback_used": false,
  "negative_control": "pass",
  "code_edited_by_human": false,
  "platforms_green": ["aos", "ios"],
  "device_runs": 4,
  "device_seconds": 1180,
  "human_seconds": 420,
  "agent_seconds": 860,
  "phase_breakdown": {"compile": 95, "run_aos": 410, "neg_control": 300, "run_ios": 375},
  "outcome": "green"
}
```

Як рахуються неочевидні поля:

- `code_edited_by_human` — порівняння hash файлу тесту одразу після кодогену
  (крок 3) і на кроці REPORT.
- `flaky_retries` — ретраї без змін коду (клас `env`); не входять у
  `debug_iterations`.
- `scroll_fix` — скільки разів рішення по скролу правилось (крок 3).
- `device_runs` — кількість прогонів на девайсі; головний драйвер вартості
  пайплайна, важливіший за секунди.
- `outcome` — `green` | `escalated` (вичерпано ліміт дебагу або neg-control
  fail) | `abandoned` (людина зупинила); `platforms_green` уточнює деталі.

**MR-метрики** — окремий файл `metrics/mrs.jsonl` (MR покриває набір чеків):

```json
{"ts":"...","mr_url":"...","check_ids":[12345,12346],
 "added_tests":4,"changed_tests":1,
 "created_at":"...","merged_at":"...","time_to_merge_s":86400,
 "review_iterations":2}
```

`merged_at` / `time_to_merge_s` / кількість раундів коментарів тягнуться з
GitLab API постфактум. Це wall-clock, а не витрачена увага рев'ювера — але
це єдиний дешевий проксі до величини, заради якої весь проєкт існує:
скільки коштує довести згенерований тест до мержу порівняно з написаним руками.

### 6.2. Агрегація

`scripts/metrics_summary.py` читає `runs.jsonl` + `mrs.jsonl` і друкує:

- медіану `debug_iterations`;
- % кейсів `green` без `code_edited_by_human`;
- % `negative_control: pass`;
- медіану `device_runs` і `device_seconds` до green; розподіл `phase_breakdown`;
- співвідношення корзин device / human / agent;
- розподіл `failure_classes` (окремо — частку `unknown` і `scroll`);
- частку прогонів зі `scroll_fix > 0`;
- частку `appium_fallback_used`;
- медіану `time_to_merge_s`.

### 6.3. Критерії успіху пілоту (5 кейсів)

| Метрика | Поріг |
|---|---|
| Медіана `debug_iterations` | ≤ 2 |
| `green` (всі платформи) без ручних правок коду | ≥ 3 з 5 |
| `negative_control: pass` | 5 з 5 (кожен fail — обовʼязковий розбір) |
| `abandoned` через зациклення | 0 |
| Прогонів зі `scroll_fix > 0` | ≤ 30% (інакше евристика скролу неправильна) |

Не дотягнули — це не «провал», а вхідні дані для `reflection`: розподіл
`failure_classes` покаже, куди бити.

**Вимога до вибірки.** Серед 5 кейсів **мінімум 2 зі скролом** (елемент у
нижній частині списку). Інакше пороги пройдені на нерепрезентативній вибірці
й не переносяться на реальний потік, де списки — норма.

## 8. Інтеграція з reflection та журналом

- Під час роботи скіл дописує рішення/тупики в активний журнал
  `.kiro/reflections/journals/` (правило `session-journal`).
- Наприкінці — `reflection` розкладає уроки. Уроки, специфічні для генерації
  тестів (евристики мапінгу, типові падіння, платформні нюанси, скрол-патерни),
  йдуть в **окремий файл** `references/lessons.md`.
- **`conventions.md` — недоторканний**: автозаписи агента туди не потрапляють.
  Дрейф довідника відносно кодової бази закривається тим самим reflection:
  урок «компонент X поводиться інакше» → `lessons.md`; правки самого
  `conventions.md` — лише руками.
- Метрики (розділ 6) — кількісний вхід для reflection: розподіл
  `failure_classes` і частка `scroll_fix` кажуть, які правки скіла дадуть
  найбільший ефект.

## 13. Рішення (закриті)

Раніше — «відкриті рішення за людиною». Закриті 2026-07-25 (див.
`DECISIONS.md` — там рішення, обґрунтування і наслідки для реалізації).
Нижче — підсумок; повний контекст кожного пункту лишено для історії.

**13.1. Kiro CLI vs IDE → CLI.** Закрито на користь CLI (розділ 0);
передпілотна перевірка #6637 лишається блокуючим чеком розділу 0.

**13.2. Модель володіння тестом → TM як source of truth.** При дрейфі
додатка тест **регенерується** з ТМ, а не правиться руками як людський.
Наслідки: (1) потрібен ре-ген воркфлоу — повторний виклик `/gen-test` на
тому самому `checkId` детермінує ті самі рішення плану, де це можливо;
(2) кожна регенерація недетермінована на рівні коду → проходить рев'ю
заново; (3) кодоген усе одно тримає ідіоматичність (спрощує diff при
регенерації), але це вже не єдиний пріоритет.

**13.3. Live-інспекція через appium-mcp → прибрано з пайплайна.** Дебаг
працює **виключно** з артефактів падіння Selenide: `automation.log`,
`surefire-reports` і дамп `UIAssertionError` (**локатор + скріншот + page
source** у момент падіння). Агент `ui-test-debugger` **сам** знаходить і
чинить локатори з цього page source. Appium/DebugPause/attach **не
піднімаються**. `unknown` → ескалація людині. Наслідки для реалізації:
- `ui-test-debugger` не має тулів appium-mcp; тули = read + shell;
- утиліта `DebugPause` **не будується** (пункт 4 роадмепу знято);
- крок 6 пайплайна не має гілки live-інспекції; метрика
  `appium_fallback_used` лишається завжди `false` (кандидат на видалення
  зі схеми після пілоту).

**13.4. iOS-верифікація → 100% на пілоті.** Лишаємо обовʼязкову iOS-
верифікацію для cross-platform перевірок. Вибірковість — кандидат у v2
(розділ 12) після стабільного pass.

**13.5. Шаблон MR → окремий `gen-test.md`.** Заводимо окремий шаблон
`.gitlab/merge_request_templates/gen-test.md` (людський шаблон не чіпаємо;
згенеровані MR упізнаються з першого погляду). Заготовка шаблону
постачається зі скілом:
`.kiro/skills/gen-test/references/mr-template.gen-test.md` — людина копіює
її у `.gitlab/` цільового репо (одноразова установка). `mr-composer`
читає й заповнює **саме цей** шаблон (імʼя зафіксоване).

**13.6. Дефолт скролу → scroll-always (no-op на видимому).** Прийнято, що
`scroll to element` на вже видимому елементі — **no-op**. Тому за невідомої
позиції дефолт: **обгортаємо взаємодію скролом** (знімає цілий клас рішень
ціною кількох зайвих жестів). Правило зафіксоване в `references/codegen.md`;
метрика `scroll_fix` контролює, чи не зайвий скрол додається.

**13.7. Рев'ю згенерованих тестів → повне рев'ю на пілоті.** «Зелений +
neg-control» **не** заміняє рев'ю на пілоті: кожен згенерований тест іде в
повне людське рев'ю. `time_to_merge_s` (6.1) міряє реальну ціну. Окремо —
віддати пілотні тести одному-двом скептикам з команди (бай-ін важливіший за
цифри 6.3). Пом'якшення гейта до «зелений + neg-control без повного рев'ю» —
рішення після пілоту за даними `time_to_merge_s`.

**13.8. A/B «моноліт vs три агенти» → опційний вимір на пілоті.** Не
блокує реалізацію. На 2–3 з 5 пілотних кейсів додатково прогнати той самий
чек монолітом і порівняти `agent_seconds` та якість. Різниця в межах шуму →
складність трьох агентів відкладається (вхід у розділ 12).
