# codegen — CODEGEN (крок 3)

Генерація тест-класу **строго за `conventions.md`** (steering цільового репо —
вичерпний довідник DSL/PbComponents). Тут — лише чек-ліст і специфічні для
gen-test правила. Авторитет: `DESIGN.md` крок 3.

## Чек-ліст (з conventions.md)
- [ ] Клас наслідує `BaseTest()`, має `@Feature("...")` на рівні класу.
- [ ] Метод: `@Test(description="укр")`, `@Owner("LDAP")`, `@TMId(<checkId>)`,
      назва `test_XX_<TMId>`.
- [ ] Взаємодія з UI — лише дозволені DSL: `screen{}`, `navigate{}`, `auth{}`,
      `stubFor{}`, `confirmation{}`, `visualTrack{}`, `api{}`, `device{}`.
- [ ] Дані всередині методу; user заданий явно (`Users.TEST_APPLE`); картка —
      цілим обʼєктом через `findCard{}`; стаби — лише з `JsonFilePath`.
- [ ] UI-елементи — через `PbComponents`, не базові локатори.
- [ ] Файл у `src/test/kotlin/tests/<feature>/` (feature — з мапи скаута).

## Головні правила
- **Еталон — `template_test` від скаута**: генеруй «за зразком найближчого
  існуючого тесту», не з нуля. Немає template → генерація з `conventions.md`
  + приклади з мапи, з підвищеною увагою на чекпоінті.
- **Не галюцинувати**: немає екрана/компонента → **ФЛАГ** і зупинка/питання,
  не вигадка.
- **API бібліотек не уточнюємо зовнішніми джерелами** (context7 тут зайвий):
  усе потрібне — у репозиторії (мапа скаута + template).
- **Regen-friendly** (рішення 13.2 — ТМ source of truth): стабільний порядок
  полів, стабільні імена стабів/методів, ідіоматичний код — щоб diff
  регенерації був мінімальним і читабельним.
- Після кодогену **зафіксувати hash** згенерованого файлу (для метрики
  `code_edited_by_human`, розділ 6): напр. `sha256sum <file>` у
  `target/gen-test/`.

## Колізія стабів
Файл маппінгу з такою назвою вже існує → **не перезаписувати й не
перейменовувати самовільно**. Ескалація людині: «переюзати наявний / створити
під новою назвою (запропонувати)». Рішення фіксується в плані.

## Traceability-карта (верифікація відповідності ТМ)

Щоб «тест відповідає ТМ» було **перевіряним**, а не сподіванням: для кожного
`step`/`expected` спека — рядок/ассерт тесту, що його покриває. Карта пишеться
в план (`plan-<checkId>.md`) і виноситься в evidence-блок MR — ревьюер звіряє
карту, а не перекладає ТМ заново.

```
TM step 1 (<expected>) → <навігація/дія у тесті>
TM step 2 (<expected>) → assert <...>            ← ЦІЛЬОВИЙ (мутація neg-control)
TM step 3 (<expected>) → assert <...>
```

- Познач **цільовий** `expected` — саме його ассерт мутує негативний контроль
  (крок 7). Кожен `expected` має мати покриття; непокритий `expected` → ФЛАГ.
- Карта — regen-friendly якір: при регенерації (13.2) звіряємо, що покриття
  збереглось.

## Скрол — штатна евристика, не gap

**Важливо:** `scroll to element` скролить до **відомого** локатора компонента
з Page Object (його мапить `repo-scout`) — це не «скрол у невідомість».
«Скрол до невідомого» виникає лише коли компонента **немає** в Page Object
(→ ФЛАГ, крок нижче) або локатор **невірний** (ловить дебаг: static dump, а
для off-screen — reveal-скан, `run-and-debug.md`).

У проєкті **є** `scroll to element`. Правило:
- елемент у **верхній** частині екрана → взаємодія без скролу;
- елемент **ближче до низу** → скрол додається **одразу в метод взаємодії** з
  елементом, а не окремим кроком сценарію.

### Джерела позиції (за спаданням дешевизни)
1. **Скаут** (`scrolled_elements`): до цього/аналогічного елемента вже
   застосовується скрол → застосовуємо. Основне джерело, безкоштовне.
2. **Template-тест**: як влаштована взаємодія з тим самим екраном поруч.
3. **Невідомо → ДЕФОЛТ: scroll-always** (рішення 13.6).

### Дефолт: scroll-always (рішення 13.6)
Прийнято, що `scroll to element` на **вже видимому** елементі — **no-op**
(не свайпає). Тому за невідомої позиції: **обгортаємо взаємодію скролом**.
Це знімає цілий клас рішень ціною кількох безпечних жестів.

> ⚠️ Дефолт коректний **лише** доки no-op-припущення тримається. Якщо
> `scroll to element` почне свайпати безумовно — дефолт небезпечний, і правило
> міняється на «unknown → флаг у план». Сигнал про це — метрика `scroll_fix`
> (нижче): частка > 30% означає, що припущення хибне.

## Метрика scroll_fix
Скільки разів рішення по скролу довелось правити (додати відсутній / зняти
зайвий) у дебазі або людиною. Частка прогонів зі `scroll_fix > 0` має бути
≤ 30% (поріг 6.3). Передається у `log_run.py` як поле `scroll_fix`.

## Наслідок для дебагу
Підклас `locator` «елемент поза вьюпортом» → авто-фікс першої ітерації
(«обгорнути скролом»), без жодної live-інспекції (її й немає — рішення 13.3).
