# mr — MR (крок 10, окрема команда /gen-test mr)

Не частина автоматичного пайплайна: запускається окремо, коли людина вирішила,
що набір тестів готовий до рев'ю. Делегується агенту `mr-composer`. Авторитет:
`DESIGN.md` крок 10 + рішення **13.5** (окремий шаблон) і **13.7** (повне рев'ю).

## Шаблон — окремий gen-test.md (рішення 13.5)
- Джерело правди: `.gitlab/merge_request_templates/gen-test.md` у цільовому
  репо. Заготовка постачається зі скілом:
  `references/mr-template.gen-test.md` — людина копіює її у `.gitlab/`
  **одноразово**.
- Імʼя зафіксоване: завжди `gen-test.md`. Немає в `.gitlab/` → зупинитись і
  попросити людину поставити заготовку.
- GitLab підставляє шаблон лише в UI. Через API/MCP `mr-composer` **сам**
  читає `gen-test.md`, заповнює і віддає готовий текст у `description`.

## Правила заповнення
- Лише секції, під які є дані; секції **не видаляти й не переставляти**.
- Чек-листи рев'ювера агент **не відмічає**.
- Мова — як у шаблоні.
- Блок доказів у маркерах `<!-- gen-test:evidence -->` …
  `<!-- /gen-test:evidence -->`; при оновленні регенерується **лише** він,
  правки людини поза маркерами не затираються.

## Цифри — скриптом (не моделлю)
```bash
python3 .kiro/skills/gen-test/scripts/mr_stats.py --base <base_branch>
```
Повертає JSON (`added_tests`/`changed_tests` з `tm_ids`, `files_*`,
`stubs_added`). `mr-composer` лише розкладає готовий JSON по шаблону.

## Блок доказів
Для кожного TMId — платформи, `negative_control`, `debug_iterations`,
`scroll_fix`, `reveal_used`, посилання на прогін. Джерело — рядки
`metrics/runs.jsonl` по цих `check_id`. Плюс **traceability-карта**
(step/expected → ассерт, з планом `plan-<checkId>.md`): ревьюер звіряє
покриття ТМ по карті, а не перекладає перевірку заново. Рев'ювер бачить,
**що саме перевірено** і **що цим покрито**.

## Гейт (обовʼязковий)
MR **не створюється**, якщо для якогось TMId у діфі немає рядка в `runs.jsonl`
з `outcome=green` **і** `negative_control=pass`. Не пройшло → повернути
список TMId і зупинитись.

## Рев'ю (рішення 13.7)
На пілоті «зелений + neg-control» **не** заміняє повне людське рев'ю — це
**вхід** у нього. `time_to_merge_s` (6.1) міряє реальну ціну. Пом'якшення
гейта — рішення після пілоту за даними метрик.

## Гранулярність
Пілот — **MR на чек** (чистіша метрика рев'ю); потік — на блок.

## Після створення
Рядок у `metrics/mrs.jsonl`: `mr_url`, `check_ids`, `added_tests`,
`changed_tests`, `created_at`. `merged_at`/`time_to_merge_s`/раунди —
з GitLab API постфактум.
