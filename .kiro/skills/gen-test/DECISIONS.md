# gen-test — закриті рішення

Журнал закриття відкритих рішень розділу 13 дизайн-документа (`DESIGN.md`).
Дата: **2026-07-25**. Кожен пункт: рішення → обґрунтування → наслідки для
реалізації. Це доповнення до розділу 10 («Прийняті рішення») дизайну.

---

## 13.1 — Платформа виконання: **Kiro CLI**

Пайплайн виконується через Kiro CLI, не через IDE. Причина — issue #6637: в
IDE поле `model` з frontmatter кастомного сабагента ігнорується при
програмному виклику, і вся економія на дешевих моделях (розділ 5) зникає.

**Наслідок:** передпілотна перевірка #6637 (розділ 0) лишається **блокуючим**
чеком. Поки не підтверджено, що `model` на агента застосовується — реалізацію
агентів не запускати в бій.

---

## 13.2 — Володіння тестом: **ТМ як source of truth**

Коли додаток змінився і згенерований тест упав — тест **регенерується** з
TestManager, а не доживає як рукописний, що правиться руками.

**Наслідки для реалізації:**
- Потрібен ре-ген воркфлоу: повторний `/gen-test <checkId>` на тому самому
  чеку має бути максимально детермінованим на рівні **плану** (той самий
  user/card/stub-вибір за тих самих вхідних даних) — план пишеться у файл
  (`plan-<checkId>.md`), рішення фіксуються, щоб регенерація не «плавала».
- Регенерація недетермінована на рівні коду → кожен ре-ген проходить рев'ю
  заново (узгоджено з 13.7).
- Кодоген тримає ідіоматичність, але вже **не** як єдиний головний пріоритет:
  головне — щоб diff регенерації був читабельним і мінімальним.
- `references/planning.md` і `references/codegen.md` фіксують це як
  «regen-friendly»: стабільний порядок полів, стабільні імена стабів/методів.

## 13.3 — Live-інспекція через appium-mcp: **прибрано з пайплайна**

Дебаг працює **виключно** з артефактів падіння Selenide. Appium/DebugPause/
attach **не піднімаються** в пілоті (і поки що взагалі).

Джерела для дебагу:
- `target/logs/automation.log` (logback, повний лог прогону);
- `target/surefire-reports/` (звіти TestNG);
- дамп `UIAssertionError` від `toSelenideUiAssertionError()` — містить
  **локатор + скріншот + page source** у момент падіння.

Агент `ui-test-debugger` **сам** знаходить і чинить локатори з цього page
source (пріоритет стратегій — за `mobile-test-standards.md`:
accessibility id > id > платформні > xpath). Скріншот — візуальний контекст.

**Наслідки для реалізації:**
- `ui-test-debugger` **без** тулів appium-mcp: `tools = [read, shell]`.
- Утиліта `DebugPause` у тест-інфрі **не будується** (пункт 4 роадмепу знято).
- Крок 6 пайплайна не має гілки live-інспекції; клас `unknown` → одразу
  ескалація людині зі зведенням діагнозів.
- Клас `scroll` закривається евристикою кодогену (13.6), не інспекцією.
- Метрика `appium_fallback_used` завжди `false` — лишена у схемі як
  сумісність, кандидат на видалення після пілоту.
- Опційно можна переюзати наявний у репо скіл `screen-analyzer` для
  офлайн-аналізу дампа page source + скріншота (він саме під це й є), але це
  **не обовʼязково** для пайплайна.

## 13.4 — iOS-верифікація: **100% на пілоті**

Обовʼязковий iOS-прогін після зеленого AOS для cross-platform перевірок
лишається. Готовність тесту = зелені **всі** платформи його перевірки.

**Наслідок:** вибіркова iOS-верифікація — кандидат у v2 (розділ 12), вмикати
після стабільного pass за даними метрик.

## 13.5 — Шаблон MR: **окремий `gen-test.md`**

Заводимо окремий MR-шаблон замість переюзу людського. Причини: людський
шаблон не чіпається; згенеровані MR упізнаються з першого погляду (корисно
для метрики часу рев'ю і для скептиків).

**Наслідки для реалізації:**
- Заготовка шаблону постачається зі скілом:
  `.kiro/skills/gen-test/references/mr-template.gen-test.md`.
- Одноразова людська установка: скопіювати заготовку в
  `.gitlab/merge_request_templates/gen-test.md` цільового репо. Після цього
  файл у `.gitlab/` — **людське джерело правди** (як і решта шаблонів).
- `mr-composer` читає й заповнює **саме** `gen-test.md` (імʼя зафіксоване в
  `mr-composer.md`), не «обирає відповідний».

## 13.6 — Дефолт скролу: **scroll-always (no-op на видимому)**

Прийнято, що `scroll to element` на вже видимому елементі — **no-op**
(не свайпає). Тому за **невідомої** позиції елемента дефолт:
**обгортаємо взаємодію скролом**. Це знімає цілий клас рішень ціною кількох
зайвих (безпечних) жестів.

Порядок джерел позиції лишається (розділ 3, крок 3): скаут `scrolled_elements`
→ template-тест → **дефолт scroll-always**.

**Наслідки для реалізації:**
- `references/codegen.md` фіксує правило й дефолт.
- Метрика `scroll_fix` контролює зайві скроли: частка прогонів зі
  `scroll_fix > 0` має бути ≤ 30% (поріг 6.3), інакше припущення про no-op
  хибне і дефолт треба міняти на «unknown → флаг у план».

## 13.7 — Рев'ю згенерованих тестів: **повне рев'ю на пілоті**

«Зелений + neg-control» **не** заміняє людське рев'ю на пілоті. Кожен
згенерований тест іде в повне рев'ю.

**Наслідки для реалізації:**
- Гейт MR (`mr-composer`) лишається: MR не створюється без
  `outcome=green` + `negative_control=pass` для кожного TMId — це **вхід** у
  рев'ю, не заміна йому.
- `time_to_merge_s` (6.1) міряє реальну ціну «написати → відрев'ювати».
- Процес: пілотні тести віддати одному-двом скептикам з команди (їх бай-ін
  важливіший за цифри 6.3).
- Пом'якшення до «green+neg-control без повного рев'ю» — рішення **після**
  пілоту за даними `time_to_merge_s`.

---

## 13.8 — A/B «моноліт vs три агенти»: **опційний вимір на пілоті**

Не блокує реалізацію. На 2–3 з 5 пілотних кейсів додатково прогнати той самий
чек монолітом (один агент, повний контекст) і порівняти `agent_seconds` та
якість із трьохагентною схемою.

**Наслідок:** різниця в межах шуму → складність трьох агентів на пілоті не
окупається, відкладаємо (вхід у розділ 12). Реалізацію трьох агентів це не
блокує — вимір робиться поверх готового пайплайна.
