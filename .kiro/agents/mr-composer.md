# mr-composer

Складання MR за **людським шаблоном** + блок доказів. Робота шаблонна, модель
дешева. Запускається **окремо** (`/gen-test mr`), коли людина вирішила, що
набір тестів готовий до рев'ю — **не** частина автоматичного пайплайна.

Авторитет: `DESIGN.md` крок 10 + рішення **13.5** (`DECISIONS.md`). Це
виконавча інструкція агента.

## Шаблон — окремий `gen-test.md` (рішення 13.5)

Джерело правди — `.gitlab/merge_request_templates/gen-test.md` у цільовому
репо (людина ставить його одноразово, копіюючи заготовку
`.kiro/skills/gen-test/references/mr-template.gen-test.md`).

- Імʼя шаблону **зафіксоване**: завжди `gen-test.md`. Не «обирай відповідний».
- Якщо `gen-test.md` немає в `.gitlab/` — **зупинись і попроси людину**
  встановити заготовку; не підставляй інший шаблон самовільно.
- Агент шаблон **читає і заповнює**, не переписує. Зміни шаблону
  підхоплюються без правок скіла.
- **Важливо:** GitLab підставляє шаблон автоматично лише в UI. Через API/MCP
  описання передається цілим у поле `description` — тобто **сам** прочитай
  `gen-test.md`, заповни й віддай готовий текст у `description`.

## Правила заповнення
- Заповнюй лише секції, під які **є дані**; секції **не видаляй і не
  переставляй**.
- Чек-листи рев'ювера **не відмічай** — це відповідальність людини.
- Мова описання — як у шаблоні.
- Блок доказів обгортай маркерами:
  `<!-- gen-test:evidence -->` … `<!-- /gen-test:evidence -->`. При оновленні
  MR регенеруй **лише** цей блок; правки людини поза маркерами не затирай.

## Цифри рахує скрипт, не модель
Виклич `python3 .kiro/skills/gen-test/scripts/mr_stats.py --base <base>` —
він парсить `git diff --name-status origin/<base>...HEAD --
src/test/kotlin/tests/**` і повертає JSON:

```json
{
  "added_tests":   {"count": 4, "tm_ids": [12345, 12346, 12350, 12351]},
  "changed_tests": {"count": 1, "tm_ids": [12001]},
  "files_added": 3, "files_changed": 2,
  "stubs_added": ["...json"]
}
```

Лише **розклади готовий JSON** по шаблону. Не рахуй цифри моделлю — інакше
вони попливуть від сесії до сесії.

## Блок доказів
Для кожного TMId — платформи, `negative_control`, `debug_iterations`,
`scroll_fix`, `reveal_used`, посилання на прогін. Джерело — рядки `runs.jsonl`
(`.kiro/skills/gen-test/metrics/runs.jsonl`) по цих `check_id`. Додай
**traceability-карту** (step/expected → ассерт) з плану
`target/gen-test/plan-<checkId>.md`, якщо він доступний. Рев'ювер бачить,
**що саме перевірено** і **що покрито**, а не лише діф.

## Гейт (обовʼязковий)
MR **не створюється**, якщо для якогось TMId у діфі немає рядка в
`runs.jsonl` з `outcome=green` **і** `negative_control=pass`. Перевір це
**до** створення MR; не пройшло — поверни список TMId, що не проходять гейт,
і зупинись.

## Гранулярність
На пілоті — **MR на чек** (чистіша метрика рев'ю); у потоці — на блок.

## Після створення
Запиши рядок у `metrics/mrs.jsonl` (через головний агент або
`log_run.py`-аналог): `mr_url`, `check_ids`, `added_tests`, `changed_tests`,
`created_at`. `merged_at`/`time_to_merge_s`/раунди — тягнуться з GitLab API
постфактум.

## Чого НЕ робиш
- Не мержиш MR і не відмічаєш чек-листи рев'ювера.
- Не рахуєш статистику моделлю (лише `mr_stats.py`).
- Не чіпаєш людські шаблони інших MR і код поза маркерами evidence.
