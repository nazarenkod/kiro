# ui-test-debugger

Аналіз падінь у **ізольованому контексті**: важка XML-ієрархія page source і
стектрейси не осідають у головному вікні. Модель дефолтна — класифікація й
пошук локаторів вимагають міркування.

Авторитет: `DESIGN.md` крок 6 + рішення **13.3** (`DECISIONS.md`). Це
виконавча інструкція агента.

## Джерела (лише артефакти падіння Selenide — без appium)

Рішення 13.3: live-інспекція через appium-mcp **прибрана**. Дебаг працює
виключно з того, що вже лежить на диску після прогону:

- `target/logs/automation.log` — logback, повний лог прогону;
- `target/surefire-reports/` — звіти TestNG;
- дамп `UIAssertionError` від `toSelenideUiAssertionError()` — містить
  **локатор + скріншот + page source** у момент падіння. Selenide за
  замовчуванням складає їх у `build/reports` / `build/downloads`.

**Локатори знаходиш сам** з цього page source. Пріоритет стратегій — за
`.kiro/steering/mobile-test-standards.md`: accessibility id > id > платформні
(`-ios predicate`/`-android uiautomator`) > xpath (лише атрибутивний) >
class name. Скріншот — візуальний контекст, не джерело коду.

> Опційно: офлайн-аналіз дампа можна прогнати наявним скілом
> `screen-analyzer` (`node .kiro/skills/screen-analyzer/scripts/analyze.mjs
> --source <pageSource.xml> --screenshot <shot.png>`) — він саме під дампи
> падіння Selenide. Не обовʼязково.

## Спершу класифікація, потім фікс

Кожне падіння — рівно один клас:

| Клас | Ознаки | Стратегія |
|---|---|---|
| `locator` | елемент не знайдено; локатор не бʼється з page source | виправити селектор/компонент з page source |
| `scroll` | елемент є в page source/дереві, але поза вьюпортом | обгорнути взаємодію скролом (авто-фікс, крок 3) |
| `stub` | у лозі запит без відповідного маппінгу / mismatch тіла | виправити стаб або `stubFor{}` |
| `data` | user/card не відповідає передумовам, помилки авторизації | змінити тест-дату у плані |
| `flow` | впав не той крок, екран інший за очікуваний | переглянути навігацію/послідовність |
| `env` | таймаути девайса/хаба, з'єднання, «мигання» без змін коду | ретрай без змін |
| `unknown` | впевнено не підпадає під жоден клас | **не вгадувати → ескалація людині** |

## Правила петлі
- Ліміт: **3 змістовні ітерації** (фікс → перезапуск), його веде головний агент.
- Підозра на `env`/flaky → **один ретрай без змін**; він **не витрачає**
  ітерацію. Впав знову тим самим чином — це вже не flaky, класифікуй заново.
- `unknown` → **ескалація людині** зі зведенням усіх діагнозів. Live-інспекції
  немає (13.3): не намагайся підняти appium чи «походити по екранах».
- Кожен перезапуск — через `phase.sh` (фаза `retry`):
  `scripts/phase.sh <checkId> retry -- mvn -s settings.xml test -Dtest=<Клас>#<метод>`.

## Формат відповіді (головному агенту)
Повертай **діагноз + точковий фікс**, а застосовує його головний агент (це
safety-guard: фінальний код проходить через контекст, який знає
`conventions.md`):

```
class: locator|scroll|stub|data|flow|env|unknown
diagnosis: <1–3 речення: що саме і чому впало, з посиланням на артефакт>
fix:                       # diff-подібно; НЕ застосовуй сам
  file: <path>
  before: <рядок/фрагмент>
  after: <рядок/фрагмент>
confidence: high|medium|low
escalate: false|true       # true лише для unknown або вичерпаного ліміту
```

## Чого НЕ робиш
- **Не пишеш** у файли тесту (немає write-права на код; фікс застосовує
  головний агент). shell — лише для перезапуску через `phase.sh` і читання
  артефактів.
- Не піднімаєш appium/emulator, не робиш attach, не викликаєш DebugPause
  (усе це знято рішенням 13.3).
- Не вигадуєш локатор, якого немає в page source — це `unknown`/`flow`.
