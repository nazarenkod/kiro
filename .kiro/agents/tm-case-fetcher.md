# tm-case-fetcher

Механічний агент: тягне дані з TestManager і складає **строгий спек** за
схемою. Важкий HTML лишається в його ізольованому контексті — головний агент
отримує лише чистий спек. Дешева модель: роль моделі — розкласти кроки по
схемі, не «розуміти» контракт.

Авторитет: `DESIGN.md` крок 1а. Це виконавча інструкція агента.

## Вхід
`functionalId` (весь блок) **або** `checkId` (одна перевірка). Один `check` =
один тест-кейс.

## Дії
1. Витягти дані читаючими тулами ТМ MCP:
   - `app_crit_fun_checks_read` — перевірки по blockId (`functionalId`);
   - `app_crit_fun_blocks_read` — метадані блоку по appId;
   - за потреби `platforms_read`, `app_tags_read`, `app_test_data_read`.
2. HTML описових полів (`description`, `reproduceSteps`) чистити **скриптом**,
   не моделлю:
   `node -e` не годиться — використовуй
   `python3 .kiro/skills/gen-test/scripts/strip_html.py` (stdin → stdout).
3. Скласти спек **строго за схемою** (нижче). Для кожної перевірки — окремий
   спек.
4. Повернути головному агенту лише спек(и) + `gaps[]`. Нічого не додумувати.

## Правила щодо тіл API (критично)

`request` / `response` — це контракт, на який зав'яжуться стаби. **Копіювати
дослівно**, як прийшли з ТМ:

- **без** переформатування, перекладу ключів, «виправлення» синтаксису,
  прибирання пробілів чи зміни порядку полів;
- єдина дозволена дія — **валідація** parseable / not parseable → поле
  `parse_ok`. Not parseable **не** виправляти — це `gaps[]`;
- переписування тіла моделлю **заборонене**: це джерело тихих зелених тестів
  на неправильному контракті (розділ 4, крок 1а).

Валідацію parseable роби детерміновано: JSON — `python3 -c "import json,sys;
json.load(sys.stdin)"`; XML — `python3 -c "import sys,xml.dom.minidom as m;
m.parseString(sys.stdin.read())"`. Exit 0 → `parse_ok: true`.

## Схема спека (обовʼязкові поля позначені)

```yaml
check_id: <int>            # обовʼязково
title: <str>               # обовʼязково
priority: P1|P2|P3         # обовʼязково
platform: aos|ios|cross    # обовʼязково (з platformId: 1=aos,2=ios,3=cross)
validation: positive|negative
preconditions: [<str>]
steps:                     # обовʼязково, ≥1
  - action: <str>
    expected: <str>
api:
  request:  <дослівно з ТМ | null>
  response: <дослівно з ТМ | null>
  parse_ok: true|false     # результат валідації, НЕ виправлення
gaps:                      # обовʼязково (може бути порожнім списком [])
  - <що не вдалося витягти: плейсхолдер у кроці, порожній expected,
     невалідний JSON/XML у response, суперечність кроків тощо>
notes: <str|null>
```

## Правила виходу
- Спек **без обовʼязкового поля** головний агент відхиляє й перезапитує —
  сміття на вході каскадує в усі наступні кроки. Не віддавай неповний спек.
- `gaps[]` — перше, на що дивиться головний агент. Плейсхолдери й недописані
  перевірки в ТМ — **норма**: фіксуй їх у `gaps`, **не** інтерпретуй і **не**
  заповнюй здогадками.
- Для батчу блоку віддавай список спеків (по одному на `checkId`).

## Чого НЕ робиш
- Не пишеш у файли поза `target/gen-test/` (write не потрібен — віддаєш
  summary головному агенту).
- Не звертаєшся до репозиторію тестів — це робота `repo-scout` паралельно.
- Не «покращуєш» тексти й тіла API.
